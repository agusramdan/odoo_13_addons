# ADDONS13-46 — Addendum keputusan analis berdasarkan delegasi Owner

Tanggal: 24 Oktober 2026
Issue: ADDONS13-46 (`0932b9ca-60ee-44b7-8c88-3e98a173b15b`)
Scope: hanya addon `amr_resource`.

## Otoritas dan status

Atas instruksi Owner agar Analis menentukan pilihan berdasarkan standar yang tersedia dan menghemat waktu Owner, addendum ini menetapkan **baseline desain konservatif** untuk menutup pilihan PRD D-01–D-11. Ini keputusan desain Analis berdasarkan delegasi Owner, bukan kutipan Lead dan bukan keputusan Lead yang telah diverifikasi.

Berlaku untuk rancangan kandidat v1 saja. Ini bukan penerimaan Step 0 oleh Lead, bukan authorization coding/test, bukan risk acceptance, bukan verdict Code Review/Security/UAT, dan bukan izin akses QA/production. PRD/UAT awal tidak ditimpa; addendum ini dibaca sebagai revisi keputusan yang terikat pada versi PRD/UAT sebelumnya. Karena acceptance Lead atas hash sebelumnya tidak otomatis berpindah ke revisi ini, Lead perlu meninjau hash revisi/addendum sebelum Step 1.

## Keputusan desain D-01–D-11

**D-01 — Profil token.** Untuk autentikasi user, terima hanya OAuth JWT access token sesuai profil RFC 9068 atau opaque access token melalui introspection profil. Tolak ID Token, HS/shared-secret JWT, JWT tak bertipe, dan token class lain. JWT diwajibkan memiliki `typ=at+jwt` (atau media-type ekuivalen yang ditetapkan profil), `iss`, `aud`, `exp`, `iat`, `jti`, `sub`, dan `client_id`; `nbf` divalidasi bila hadir. Algoritma baseline hanya RS256 dengan RSA public key dari JWKS profil; algoritma/key type lain ditolak. `exp` wajib belum lewat, `iat` tidak boleh di masa depan, `nbf` harus sudah berlaku; clock leeway 0. Opaque token hanya diterima pada profil introspection terpilih dari registry; respons harus JSON object dengan `active` boolean tepat `true`, `sub`, `aud`, `client_id`, serta claim wajib profil; `iss` ditambatkan ke issuer endpoint terdaftar bila tidak dikembalikan. `azp` mengikuti D-04. Tidak ada fallback otomatis antar kelas token. Token class yang tidak sesuai ditolak sebelum resolver.

**D-02 — Trust registry dan mode.** Mendukung satu atau lebih issuer terdaftar, tetapi setiap issuer harus unik secara global dan lookup harus menghasilkan tepat satu record aktif dengan string exact (tanpa normalisasi slash/case/prefix). Issuer dari token hanya lookup hint; unknown, malformed, inactive, atau duplikat ditolak sebelum DNS/HTTP/credential access. Tidak ada fallback ke `web.base.url`. V1 memakai endpoint statis dari registry saja; Discovery tidak digunakan. Tidak ada auto-registration dari token. Migrasi key-indirection lama harus eksplisit, versioned, idempotent; jangan mengartikan key konfigurasi sebagai URL literal. Local issuer pun harus terdaftar dan melewati validasi token yang sama; tidak ada local bypass. Local profile tidak boleh melakukan HTTP loopback: key lokal harus dipilih melalui protected key reference yang dikonfigurasi administrator.

**D-03 — Kebijakan endpoint/transport.** Pada v1, endpoint dikonfigurasi statis oleh administrator. Hanya HTTPS dengan verifikasi TLS aktif; URL tanpa userinfo dan hanya port 443. Tolak alamat loopback/private/link-local/multicast/reserved serta hostname yang mengarah ke alamat tersebut; validasi DNS/alamat saat koneksi. Redirect dinonaktifkan. Jangan meneruskan bearer token/credential lintas-origin. Timeout connect 3 detik, read 5 detik, total 8 detik; retry 0; ukuran respons maksimum 1 MiB. Terapkan aturan yang sama pada metadata, token, introspection, standalone JWKS, dan PyJWKClient; jalur yang tidak dapat mematuhinya tidak didukung/ditolak. Introspection selalu POST `application/x-www-form-urlencoded` ke endpoint tepercaya yang dikonfigurasi; `url` dari caller dan GET-body lama ditolak. Nilai ini pilihan kebijakan proyek, bukan bukti runtime telah menerapkannya.

**D-04 — Audience dan `azp`.** Simpan satu atau lebih audience per issuer. Untuk access token, `aud` harus string atau list string valid dan minimal satu nilai harus exact-match salah satu audience profil (ANY); missing, kosong, tipe bersarang/non-string ditolak. Duplikat konfigurasi ditolak. `azp` boleh absen hanya bila profil mengizinkan; jika hadir harus berupa satu string nonkosong yang exact-match nilai `azp` terkonfigurasi. Profil tidak valid jika mensyaratkan `azp` tetapi tidak punya nilai tunggal yang dikonfigurasi. Jangan mengimpor aturan ID Token karena ID Token ditolak untuk resource authentication.

**D-05 — Identitas user.** Gunakan hanya exact `(issuer, sub)` binding untuk autentikasi pada v1. Email/login matching tidak digunakan untuk authorization; tidak ada automatic email fallback atau auto-binding. Unbound subject ditolak sampai administrator membuat binding lewat alur konfigurasi yang diaudit. Pasangan `(issuer, sub)` harus unik. User tujuan harus aktif; machine token tidak boleh resolve ke user nonaktif. `Default` adalah pilihan tersedia, tetapi tidak dipilih otomatis untuk record baru/eksisting. Existing email mappings hanya dipertahankan setelah migrasi eksplisit ke binding; collision/ambiguity menolak migrasi, tidak diselesaikan dengan `limit=1`.

**D-06 — Fixed user dan resolver.** Fixed user hanya dari konfigurasi tepercaya, bukan claim token; harus satu `res.users` aktif, bukan superuser/public/portal, dan `company_ids` harus mencakup company aktif pada request. Resolver model-method harus berasal dari allowlist kode tetap, bukan nama model/method dari token atau konfigurasi bebas. Hasil harus tepat satu record `res.users` yang ada dan memenuhi eligibility yang sama; zero/multiple, tipe lain, exception, atau record tidak eligible ditolak. Tidak ada fallback diam-diam ke resolver lain. Jalankan tanpa `sudo()` implisit.

**D-07 — Stored Python.** Field `python_code` boleh direpresentasikan dalam desain, tetapi eksekusinya **disabled-by-default dan tidak termasuk baseline v1**. V1 memakai fixed-user atau resolver method allowlist saja. Tidak mengklaim `safe_eval` sebagai sandbox. Mengaktifkan stored Python memerlukan keputusan Owner terpisah, model threat/control yang disetujui, review manual Security pada exact code/context/config revision di unified Code Review, pembatasan izin edit/activate, dan audit actor/time/digest. Tanpa seluruh prasyarat tersebut, code tidak dieksekusi.

**D-08 — Registry access.** Buat dua group addon: `group_oidc_trust_admin` untuk issuer/audience/configuration dan `group_oidc_code_admin` untuk menulis source `python_code`; keanggotaan keduanya hanya diberikan manual kepada administrator internal yang ditunjuk. Code admin tidak otomatis memperoleh hak mengaktifkan Python. Tidak ada CRUD/read terhadap registry/code untuk public, portal, atau user biasa. Backend ACL, record rules, field access, company scope, dan RPC/public-method guard harus diberlakukan; menyembunyikan view bukan kontrol akses. Registrasi company-scoped, tidak global; lookup menggunakan company context yang efektif dan tidak fallback lintas-company. Secret hanya melalui credential reference, tidak dibaca/ditampilkan dari field biasa. Kegagalan izin harus menolak tanpa mengembalikan detail konfigurasi.

**D-09 — Cache/rollback.** V1 tidak memakai cache addon maupun library untuk token, introspection, metadata atau JWKS; nonaktifkan cache PyJWKClient dan cache helper bila tersedia. Jika jalur library tidak dapat dijalankan tanpa cache pada versi dependency yang dipin, jalur itu tidak didukung sampai adapter tanpa cache lulus review/test. Perubahan profil tidak boleh memakai data revisi lama. Rollback tuple mencakup code, schema, konfigurasi/credential references, revision/audit dan cache state. Migrasi additive, versioned, idempotent; jangan menghapus data lama sebelum backup dan restore rehearsal QA.

**D-10 — Runtime dan modul.** Target produk tetap Odoo 13 dengan Python 3.7.9 sebagaimana batas runtime proyek; dependencies harus dipin dan kompatibel dengan runtime tersebut. Kandidat hanya mengubah `amr_resource`. Test matrix mencakup dependency yang benar-benar diperlukan untuk install/import `amr_resource`; addon sibling tidak boleh diasumsikan terpasang atau kompatibel. QA harus terisolasi/disposable dengan module list, DB, runtime dan effective MRO diverifikasi sebelum Step 3. Nama host atau manifest bukan bukti runtime tersedia. Bila runtime/matrix aktual berbeda, stop dan catat mismatch sebelum mengubah ekspektasi.

**D-11 — API, errors, dan precedence.** Pertahankan public helper signatures dan bentuk return kecuali perubahan breaking disetujui dalam revisi kontrak. Token-validation/resolver failure menjadi Unauthorized generik (401 pada HTTP); jangan bocorkan token, endpoint credential, raw claims, atau exception body. Precedence tetap session → bearer → explicit params. Session yang sudah sah diterima tanpa bergantung pada bearer. Jika bearer dikirim dan invalid, reject request dan jangan fallback ke params. Jika bearer tidak ada, params hanya diterima melalui validasi credential yang ditentukan pemanggil; tidak ada fallback setelah kegagalan validasi. Perubahan UID hanya setelah principal tervalidasi; same-UID metadata behavior dipertahankan. Payload dict/context marker/get_uid langsung tidak dianggap verified tanpa provenance internal yang hanya dibuat setelah validasi.

## Dampak ke PRD/UAT

1. D-01–D-11 pada PRD ditafsirkan sebagai **RESOLVED_FOR_DRAFT_BY_ANALYST_DELEGATION** dengan nilai di atas; rekomendasi lama yang bertentangan digantikan untuk rancangan v1. Nilai ini bukan penerimaan risiko Owner.
2. UAT expected results harus mengikuti pilihan addendum ini: reject unknown/ambiguous issuer sebelum egress; hanya access token; exact trust/audience/azp; single eligible user; no invalid-token fallback; stored Python tidak dieksekusi di v1; endpoint transport policy bernilai konkret di atas.
3. UAT tetap rancangan; tidak ada test yang dijalankan. Kasus integration/runtime/ACL/RPC/rollback tetap `NOT RUN` atau `DEFERRED / NOT RUN` sampai gate dan target terotorisasi.
4. Sebelum implementasi, Lead harus menerima revisi PRD/UAT/addendum pada hash yang tepat. Instruksi Owner untuk menetapkan pilihan desain tidak menggantikan acceptance Lead dan tidak dengan sendirinya mengotorisasi QA runtime.
5. RFC 9068 mandates typed access tokens and defines the required JWT access-token claims/validation profile. This addendum intentionally selects only RS256, no clock leeway, static endpoints, and stricter local transport limits as project policy; those values are design choices, not claims that the RFC mandates them.
6. The current standards list in `/home/ubuntu/docs/standards/DEVELOPMENT-WORKFLOW.md` governs gate sequencing, candidate-bound review, QA authorization, and merge acceptance. It does not confer those approvals through this design addendum.
