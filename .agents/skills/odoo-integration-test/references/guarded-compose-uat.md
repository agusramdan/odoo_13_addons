# Guarded Compose UAT

Use this procedure when a repository provides a Docker Compose UAT template and a bounded run wrapper. It is a workflow, not a universal authorization. Keep UAT case results separate from review, acceptance and release gates.

**Authorization precedence:** The latest explicit Owner instruction controls. A plan-only, no-run, no-build, no-container or no-database instruction prohibits the corresponding action, regardless of older permissions or the automatic language below. PRD/UAT acceptance never authorizes runtime, building, pulling, database access or cleanup by itself. A direct `jalankan UAT` or `/runuat` for a uniquely identified task authorizes safe isolated synthetic disposable setup and execution within the existing accepted task scope, including an offline build when needed within that scope. It does not expand the accepted scope or override a later explicit stop or stricter task-specific rules. Arbitrary network retrieval, production data, risky cleanup and actions outside that scope require separate authorization.

## 1. Bind the candidate and accepted tests

1. Read the canonical development workflow and the exact accepted PRD/UAT revisions. Verify their paths and hashes. A direct Owner acceptance applies only to those exact bytes; a draft or matching filename is not enough.
2. Read the repository UAT template, Compose file, Dockerfile, runner/wrapper and mock tests. Record the exact accepted case IDs and the authorized target, database lifecycle, data classification, network/egress, run/retry budget and cleanup scope.
3. Identify source as a commit SHA plus all staged, unstaged and non-ignored untracked paths. Never stage, reset or clean the source worktree merely to create a test candidate.
4. For a dirty worktree, create an isolated candidate snapshot from the exact base commit plus the authorized dirty file contents. Exclude `.git`, `__pycache__`, `*.pyc`, secrets and unrelated ignored artifacts. Record every included path/status/content hash and the base SHA. Define excluded ignored-file, bytecode-file and cache-directory counts separately; reconcile each against the live Git inventory instead of reusing a remembered count. Define the candidate identity as SHA-256 of canonical JSON for the finalized manifest with only the identity field omitted; recompute it after every manifest correction, then SHA-256 the exact serialized manifest separately. Verify snapshot file hashes match the source and the source/index did not change. If the bind-mounted source includes unmanifested ignored or sensitive material, stop; do not run against an ambiguous candidate.

## Task-derived variable convention

Do not require the Owner to pre-export every `UAT_*` variable, create a repository `.env`, or fill a duplicate profile file when accepted artifacts and current Owner decisions already supply the values. Build an in-memory environment map for the wrapper using this precedence: latest explicit Owner decisions → exact accepted task profile/UAT → repository Compose, Dockerfile, lock/build metadata and test configuration → the safe derivations below. Pass it to the wrapper via a child-process environment mapping (for example, Python `subprocess.run(env=...)`), not shell interpolation or `set -x`; never print or log the map. Never allow ambient shell values to silently override accepted values; report a conflict as one grouped issue.

- **Identity and paths:** derive `UAT_TASK_ID` from the active task; `UAT_COMPOSE_FILE` from the active repo's `tests/docker-compose-uat.yml`; `UAT_SOURCE_DIR` from the verified snapshot; and `UAT_PROFILE` from accepted case class (`uat-native` for Odoo/PostgreSQL, `uat-offline` only for offline cases). Derive `UAT_COMPOSE_PROJECT` as `uat-<sanitized-task-id>-<candidate-sha-prefix>`, truncate the task slug first to stay within Compose's 63-character limit, and if occupied lengthen the hash prefix deterministically before rechecking. Never adopt pre-existing resources. Reuse this stable project for sequential attempts only after exact cleanup read-back confirms it is empty; an occupied project is a hard stop.
- **Task decisions:** `UAT_DB_NAME`, `UAT_PYTHON_RUNTIME`, accepted cases, and `UAT_MAX_RUNS` come from exact task decisions/artifacts. Reuse values already given; do not copy an example or sibling-task value.
- **Ledger and evidence:** derive a stable authorization-envelope ID from the exact accepted PRD/UAT hashes plus the task's explicit target, data/network scope, attempt cap and cleanup bounds (exclude candidate and invocation timestamp, so repeated `/runuat` calls or a new candidate cannot reset the task cap). Use `UAT_STATE_FILE` under `$HERMES_HOME/uat-state/<task>/<envelope-id>.attempts`; if the fields cannot be canonicalized, use `$HERMES_HOME/uat-state/<task>/attempts`. Derive `UAT_EVIDENCE_DIR` under `$HERMES_HOME/uat-evidence/<task>/<candidate>/<run-id>`. Keep them outside the repo and volumes; create directories mode 0700 and logs mode 0600. Check prior attempt history before initializing a ledger; never overwrite, delete, or zero an existing ledger. A reset requires a separate, direct Owner authorization. For an authorized reset, preserve the old ledger and its hash/count, append a reset-generation record bound to the task/spec/target, and create a distinct generation-specific ledger initialized at zero; keep the existing per-generation cap unless the Owner explicitly changes it. The next `/runuat` must select the recorded active generation. Reset authorization changes only the attempt budget; it does not start UAT or reset budget again on candidate/invocation changes.
- **Synthetic account and runtime identity:** derive `UAT_DB_USER` as `uat_<sanitized-task-id>` unless the accepted task profile specifies another synthetic identity; keep it within the database identifier limit and add a deterministic hash suffix when truncation is needed. Derive UID/GID from the exact pinned image's numeric `Config.User` or task build metadata; never guess from a similarly named image.
- **Resource caps:** use task-profile limits when present. Otherwise apply bounded `uat-native-conservative-v1`: Odoo 2 GiB / 1 CPU / 256 PIDs, PostgreSQL 1 GiB / 0.5 CPU / 128 PIDs, offline runner 512 MiB / 0.5 CPU / 128 PIDs. Read live Docker/host capacity first; if the host cannot safely support the selected caps, report one capacity blocker rather than remove limits or ask for each variable separately.
- **Task-scoped Odoo image:** for every task/candidate, create a fresh final Odoo image from the isolated candidate snapshot, a task-specific Dockerfile/build context, a digest-pinned approved base, the exact Odoo source commit, and the complete dependency lock. Never assign a prebuilt final Odoo image from another task to `UAT_ODOO_IMAGE`, even if its tag or labels look compatible. A local image may be used only as an approved immutable `FROM` base; the final service image must have a new task/candidate-specific tag and digest. Add build provenance labels for task ID, candidate ID, Odoo source commit, Python runtime, and dependency-lock hash; record the resulting image ID/digest.
- **Offline build gate:** after read-only preflight passes, build only if current task-scoped authorization explicitly covers that build and no later prohibition applies. Default to already-local, pinned inputs and a network-denied builder. Only when a separate, explicit task-scoped Owner authorization covers host-side retrieval may the agent retrieve the exact pinned Odoo source commit and complete dependency artifacts; verify and record every digest/hash, then build the final image from those pinned inputs. This exception does not permit network access from UAT services or authorize unrelated pulls/fetches. If inputs remain missing/unpinned or no such authorization exists, stop with one grouped `task image build inputs unavailable` blocker; do not fall back to a sibling image. `--network=none` alone is not proof that the builder cannot resolve a missing base image remotely.
- **PostgreSQL image:** for this Owner's Odoo 13 UAT workflow, use PostgreSQL 10; do not silently substitute 12/13 because another tag is cached. Inspect the exact image entrypoint and effective user against the Compose capability policy before a UAT attempt: a root-started entrypoint that uses `gosu` to switch to `postgres` can fail under `cap_drop: [ALL]` before any test runs. When an isolated, no-database image probe is separately authorized, test the actual pinned image with a network-disabled, read-only invocation such as `docker run --rm --network none --read-only --cap-drop ALL --entrypoint gosu <pinned-postgres-image> postgres id`; treat failure as a concrete compatibility blocker, not a UAT attempt. Do not weaken capabilities or edit a shared Compose template without the required scope authorization; choose and independently verify an authorized remedy before starting the database. The official `postgres:10` image is the base of record. During read-only preflight, only check whether it is local. After the other read-only gates pass, if absent, pull only that image as explicitly authorized by the Owner, without starting a container, then resolve and record its RepoDigest. If the approved security profile requires a non-root/capability-dropped service and the official image cannot satisfy it, a task-scoped derivative is allowed only when built from that exact pinned official PostgreSQL 10 base without fetching unrelated inputs; record both base and derived digests and preserve engine major version 10. Never launch using a mutable tag alone. Keep the UAT database isolated and without outbound network. PostgreSQL 10's support status is informational and MUST NOT by itself block, defer, or prevent an otherwise authorized synthetic, disposable UAT. This does not authorize production use.
- **Dependencies and commands:** resolve the complete dependency set from exact task pins, accepted build records, or repository locks. Do not use a partial addon requirements file as the runtime closure. Derive the Odoo command from accepted case IDs plus repository test discovery/config. Confirm exact Odoo 13 discovery behavior and that expected test methods actually collect; an exit-0 run with zero tests is `NOT RUN`, not PASS. If no unique command-to-case mapping exists, report one `test-command mapping` blocker. For inactive profiles, supply inert interpolation-only values if Compose requires them, but never launch/build that profile or claim its image is qualified.
- **Config and password:** generate a minimal task-scoped Odoo config in the isolated scratch run directory from repository configuration and accepted task values; do not require a hand-created path if it is fully derivable. If the current authorization explicitly covers creation and cleanup of a per-run synthetic DB credential, generate a fresh CSPRNG password under `$HERMES_HOME/uat-secrets/<task>/<candidate>/<attempt>/` in a directory mode 0700. Use file mode 0600 when all runtime consumers share the file owner UID; when isolated non-root services use distinct UIDs but a dedicated shared GID, mode 0640 is allowed only with that GID and the 0700 parent directory. Pass only its file path, never display/log the value, and remove only that exact run-owned directory during cleanup. Verify the effective UID of each consumer and destination-path traversal for individual file binds: changing a private directory to another UID can prevent the creator from completing setup or cleanup. If privileged ownership setup is necessary, use a reviewed controller from a trusted non-user-writable location, a protected parent and descriptor-relative operations; never run mutable untrusted helper code as root. Stop consumers before removing mounted files and treat partial cleanup as blocked. Otherwise use an approved local secret-store/file reference; do not invent authority to create/delete secret material. Verify the pinned image actually supports the Compose secret-file contract and how its entrypoint consumes it: a `_FILE` variable may still be expanded into a process argument. Do not print, log or expose credentials in argv; use a reviewed private configuration-file path when supported.

Resolve all derivable values in memory and finish every read-only gate first. Only after authorization, candidate, image-source/lock, capacity, command mapping, and project-isolation checks pass may the task-scoped build run. Then materialize task-scoped ledger/config/temporary secret artifacts immediately before launch. Record exact paths and permissions without secret contents; remove only run-owned temporary secret/config artifacts during authorized cleanup.

Treat absent shell variables, missing `.env`, and a missing duplicate profile file as inputs to resolve—not blockers. Report only unresolved semantic requirements (for example, no qualified active Odoo image/dependency set), not `0/N UAT_*` or a long list of variable names. Never invent an image, dependency set, test command, secret contract, or authorization scope.

## 2. Read-only environment preflight

Before starting any container or database:

- Inspect local images only. Record immutable digest, architecture and trustworthy provenance for the Odoo, PostgreSQL and runner images. A tag, image label or image name is not proof of the Python version or dependency closure. Do not pull, build, contact a registry, or start a container during a read-only preflight.
- Verify the exact Odoo/Python/dependency tuple against the accepted UAT target. Use the complete pinned dependency set, not a partial addon requirements file. If Python/API compatibility cannot be established from trusted image/build metadata without executing a container, mark it `BLOCKED / NOT PROVEN`; obtain separate explicit authorization for a bounded no-egress image probe. Do not consume the formal UAT run budget for unapproved setup probes.
- Derive the union of `UAT_*` placeholders from the Compose file and wrapper, then resolve them using the `Task-derived variable convention` above. Do not treat a missing process-environment variable or dotenv file as a blocker by itself. Validate existing config/secret reference metadata, or validate the protected run directory and generation method when those files are created per-run; never open or print secret contents. Never store secrets in repository `.env`, shell history, manifests or chat.
- Confirm the candidate bind mount points to the verified snapshot, test data is synthetic, source/config mounts are read-only, and external egress/host ports are disabled unless a specific accepted case explicitly requires them.
- Choose a unique task/candidate-scoped Compose project. Before incrementing an attempt ledger or allowing `down --volumes`, verify read-only that the exact project has no pre-existing containers, volumes or networks. Any inventory error or existing resource means stop; never adopt existing resources or run a broad prune. Sequential use of the stable task/candidate project is allowed only after exact cleanup/read-back proves it empty.
- Run only static Compose parsing/config checks with harmless dummy placeholders. Do not mistake `docker compose config -q`, image inspection or a healthy database for UAT evidence.

If, after applying the task-derived convention, an accepted hash, candidate identity, image/dependency tuple, command-to-case mapping, config/secret-file contract, isolation control, or authorization scope remains missing or ambiguous, mark the relevant case `BLOCKED`/`NOT RUN` and do not start services. A missing variable or file path that is safely derivable/generated within the approved envelope is not by itself a blocker.

## 3. Execute within the approved envelope

1. Reuse current task-scoped Owner authorization only for actions it explicitly covers, subject to later instructions. A direct `/runuat` or `jalankan UAT` authorizes safe isolated synthetic disposable setup and execution, including an offline build if needed, only within the existing accepted task scope; it does not authorize a pull or any action outside that scope. Honor explicit expiry, cancellation and limits. Bind the derived candidate and accepted case IDs in the run manifest. Require explicit scope for nonproduction target, disposable DB lifecycle, synthetic data, egress, attempt budget and exact cleanup. PRD/UAT acceptance alone is not runtime permission.
2. Use the repository's documented wrapper as the only launch path. The wrapper should enforce the total started-attempt limit through an external persistent ledger; count failed and interrupted started runs. Never treat a retry limit as an additional run limit.
3. Use no more attempts than authorized. Treat the total attempt cap and permission for automatic retry as independent decisions: raising the cap does not authorize an automatic retry when the Owner previously prohibited it. Compare the wrapper's actual enforced cap with the latest authorized cap before launch; never pass a larger cap while assuming an unverified external guard will enforce a smaller one. Do not automatically repair, change image/dependencies, retry beyond the cap, or switch candidate/target. Any change is a new preflight/authorization boundary.
4. Record each accepted case's actual result and evidence. Confirm Odoo logs show the expected tests/methods actually ran; process exit 0 alone is not proof of collection or pass. Keep mock/static checks distinct from native registry/ORM/database UAT.
5. Keep raw logs owner-only (for example, mode 0600) and treat them as potentially sensitive until reviewed/redacted. Save evidence outside ephemeral volumes; never share unsanitized logs or token-bearing output.

## 4. Cleanup and report

- On normal completion and catchable termination, cleanup must target only the exact Compose file/profile/project and only resources created by that run. Also remove only the exact task/run-scoped secret artifacts generated by that run when their lifecycle is authorized. Never remove pre-existing/shared resources or use global prune/reset commands; never clean unrelated host paths.
- Verify exact containers, networks, volumes and disposable database are absent. A failed or unverified cleanup blocks closure. Project-scoped Compose cleanup can satisfy the ownership boundary when the exact project was proven empty before launch, cleanup is confined to that project, and post-cleanup readback succeeds; do not substitute a mock exact-ID model for the actual wrapper. `SIGKILL` and host failure cannot be trapped; on recovery, inventory and clean only verified run-owned resources under the existing authorization.
- For an accepted failure-injection/cleanup oracle, bind the injection point to the exact accepted case: when it requires failure after resource creation but before the test finishes, an intentional exit after all tests completed is not equivalent. Require a reviewed injector, ordered phase evidence, the exact expected sentinel exit, and successful cleanup/readback; any arbitrary nonzero exit may be setup, test, or cleanup failure and is not an injection PASS. Use a verified structured evidence channel or parse representative Compose-prefixed output correctly rather than assuming raw service log lines are unprefixed. Check each inventory/inspection command's exit directly rather than relying on a shell pipeline whose final `sort` can mask an earlier failure; compare preservation of preexisting foreign resources without treating unrelated newly created resources as deletion. Mocked wrapper tests validate control flow only, not real Docker behavior.
- Preserve the attempt ledger and sanitized evidence outside ephemeral storage. Do not reset the budget after failure/interruption.
- Report the candidate/spec hashes, image digests/dependency set, accepted cases, attempts used/remaining, actual per-case outcomes, cleanup readback and all limitations. `NOT RUN`, `BLOCKED`, `FAIL` and `PASS` are distinct; never convert a subset or preparation check into aggregate UAT PASS.

## Direct `jalankan UAT` instruction

The bundled `resolve_uat.py` is read-only and proposes a limited configuration from an explicitly hash-bound committed JSON profile; it does not establish acceptance or authorization and cannot perform this execution workflow. All execution gates below require independent verification and a separately implemented safe controller.

When the Owner sends `jalankan UAT` or `/runuat` for the uniquely identified current task, automatically read `tests/UAT-ENVIRONMENT-TEMPLATE.md`, accepted artifacts and repository Compose configuration; assemble the task profile from those sources and current Owner decisions. A separate filled profile file, pre-exported `UAT_*` variables, and repository `.env` are not prerequisites when values can be derived safely. Run preflight and proceed through the documented wrapper if all semantic gates pass. Do not carry task-specific values into another repository or task.

- Reuse current, explicit Owner selections (such as runtime, service/database names, synthetic-only data, no egress, attempt cap and cleanup) without asking the Owner to repeat them. Verify the accepted PRD/UAT hashes and candidate identity from the current files before any state-changing action.
- Run the preflight automatically in order. If all inputs and gates pass, proceed within the exact profile; do not pause for generic or redundant confirmation.
- If a specific prerequisite is missing or unproven, stop before the first side effect, preserve `NOT RUN`/`BLOCKED`, and report the exact blocker and the least additional action needed. Ask one focused question only when an Owner-only choice changes the target, allowed action or risk boundary; never guess missing values.
- This instruction does not authorize network retrieval or pulls, image probes outside the approved UAT run, production access/data, a changed candidate/target outside accepted scope, exceeding the configured attempt limit, or cleanup beyond the exact task project. Obtain separate authorization for any such expansion. Never request or echo secret values in chat.
