# Odoo 13 unit tests without a database

For each addon, place all new isolated unit tests in `<addon>/tests/unit/`, organized as `test_*.py`; keep test files outside Odoo integration test imports. Do not modify addon initialization merely to collect unit tests. Run each addon through the skill runner with `--addon <addon-path>`. Preserve existing integration tests. For coverage, invoke `scripts/run_tests_in_docker.sh --coverage [--coverage-min PERCENT] --addon <addon-path>`. Coverage measures addon Python source, excluding tests/fixtures; default minimum is 70%. An explicit threshold in the active task story/spec overrides this default. Report exact command, interpreter, percentage, denominator, omitted files. If coverage is unavailable in the verified runtime, classify as setup-blocked; don't silently install dependencies or substitute another runtime. Check that the runner and its dependencies are available under the exact interpreter before classifying a failed invocation; a missing pytest/import is setup failure, not a test result. Before each run, read the active repository `AGENTS.md` and current task/Owner pin for the exact required interpreter. An explicit current Owner pin takes precedence over a conflicting repository `AGENTS.md`; use the repository pin only when the Owner has not set one. Use the exact selected version or classify the run as setup-blocked; matching a major/minor family is insufficient.

When a repository provides a Docker test runner, inspect its Dockerfile and dependency lock first: verify the built interpreter version and compare selected-test imports with the image's installed requirements. Treat a cached image as usable only after checking its actual interpreter and package versions against those declarations; a similar tag or matching Python version does not prove dependency parity. If it differs, rebuild from the repository's exact Dockerfile/requirements in a bounded build context, then verify the runtime and imports, or classify the suite as setup-blocked. A successful image build proves only that the declared environment built, not that addon tests can be collected. If application imports are missing, classify collection as setup-blocked; don't borrow site-packages from another image because Python ABI, OpenSSL, GLIBC, and package versions can differ. Keep a Python-version-only request scoped to the base-image change; treat adding or changing test dependencies as a separate authorized change. Pin Docker base images to a verified digest and verify Python inside the built image. Use `.devcontainer/Dockerfile.unittest` as the repository's canonical image definition; build from the repository root so the runner, examples, and addon requirements are included. If the repository provides a Docker runner, run the skill runner inside the built image; if it does not, run the skill runner in a separate container with the built image mounted at the same path as the repository root. In either case, verify that the runner sees the same interpreter and imports as the built image.

If the suite is unittest-discoverable but the prescribed runner cannot run, a direct `unittest` invocation is supplemental evidence only: run it under the same isolation hook (`install(); self_check()` from `scripts/isolation.py`), from the addon's `tests/unit` directory with an explicit `test_*.py` pattern, and report interpreter/runtime, exact command, executed count, and limitations separately from the required runner and gate verdict.

Before selecting a suite or consolidating tests from a shared legacy tree, inventory every candidate test file and its imports, references, and Odoo registration; distinguish addon-owned tests from shared fixtures and temporary probes. For each file, record its exact path and whether it is imported for Odoo integration discovery, collected by the isolated unit runner, deliberately excluded with a reason, or legacy/unregistered. Treat a task-specific runner as a selection, not proof of suite completeness: compare its collected file set against every standalone offline module, because a passing count can omit an unregistered offline unittest. Distinguish similarly named tests in different addons. Move only the addon-owned tests/probes authorized by scope, preserve probe bytes when relocating them, and retain shared helpers still used by other suites. Remove a legacy selector only after canonical addon-owned discovery covers its cases; replace selector-specific layout checks with addon-owned checks that do not recursively invoke their own test suite. Update active test instructions and label old selector results as historical. Run the required skill runner on the target Python; if using a different runner as a fallback, report it as supplemental evidence rather than equivalent gate completion.

Choose pure Python for extracted business rules and dependency injection; choose Odoo mocked to import an addon module that needs Odoo names. Read [mode guidance](references/modes.md) and [isolation guidance](references/isolation.md). Use the helper in `scripts/mock_odoo.py` and adapt the templates and examples to the code under test; do not claim the doubles reproduce the Odoo ORM. Test observable decisions and mocked side effects, including failure paths. When diagnosing a named failure, inspect the test body and exact assertion before calling it obsolete; a source-level test can encode a real package or security boundary, not merely an implementation detail. Trace the first exception through the current call path and compare each fake's attributes/signature with the Odoo object the code now consumes. If a stale double omits a required framework attribute, classify it as a fixture failure, make only the minimal authorized fixture correction, then rerun the focused test and complete required suite; do not attribute it to product behavior or treat the gate as green until the suite passes. Before deleting, commenting out, or weakening an existing test, compare its assertion with the accepted AC/crosswalk and current implementation, and classify behavior/security checks separately from source-layout or style checks. For a pulled or updated candidate, compare active test IDs and collected counts with its parent; commented-out tests are not skips, dispositions, or coverage. If tests are reorganized, preserve each acceptance/security invariant in active tests under the new API and record the mapping; a lower test count alone is never evidence of a passing gate. If a refactor moved behavior, rewrite the test against the layer that now owns the contract rather than preserving an obsolete file/string expectation or dropping the intent. When a source-layout test names a removed or moved file, reproduce the failure type first (assertion failure versus `FileNotFoundError`/collection error), inspect the current package registration, and derive its source set from the actual registered modules (for example, parse `models/__init__.py` imports) instead of hard-coding stale paths. Assert that the derived set is nonempty and each registered file exists, then preserve the original behavioral/security invariant over that set; do not skip a privacy or dependency-direction test merely because its former helper file disappeared. For a deprecated or renamed API, verify the supported replacement and its caller contract; update only tests that exercise the retired API, preserve required behavior assertions through the replacement, and do not invent implicit defaults unless the accepted contract requires them. Re-run the specific failures under the required runner and interpreter to verify the diagnosis, then run the full required suite after changes. If the required runner does not expose per-case diagnostics, keep it as the authoritative gate run and use a diagnostic supplement under the same isolation: invoke the same pytest arguments after `isolation.install(); self_check()`, write JUnit XML only to a tmpfs path, and parse it in memory. Project only test IDs, counts, exception types, and sanitized failure categories; never print or persist raw failure bodies, source snippets, locals, or fixture values. Label this as diagnostic evidence, not a replacement for rerunning the full required runner. When changing token-provider or cache paths, enumerate preconditions previously enforced by removed helper calls (for example, cache-key field indexing); preserve those checks explicitly and add negative tests for every affected provider/inherited provider that assert a missing required key fails before token POST, signing, or business request. When an issuance API distinguishes actor from target, test them as distinct fixtures: assert target-derived claims, preserved actor/context, and unauthorized cross-user rejection before cache/signing; do not infer system-to-target coverage from a direct `encode()` call with no target parameter or from a mocked cache wrapper. Keep an absent key distinct from a present-but-falsey value unless the accepted contract intentionally changes both. Patch dependencies where the code looks them up. Use unmistakably synthetic, purpose-labeled literals such as `test-only-client-secret` for secret/client-auth fixtures; never copy environment or production values. Keep fixture values out of logs and reports (use `[REDACTED]`), and when reviewing an existing scanner match, trace the fixture's setup and consumers before classifying it as live credential material.

Run `scripts/run_tests_in_docker.sh` from a repository development container to build/use the pinned Odoo 13 test image and execute the suite under verified Python 3.7.3. For addon tests use `scripts/run_tests_in_docker.sh --addon <addon-path>`. This requires Docker socket access and the repository mounted at `/workspace`; there is no host-Python fallback. The lower-level `python scripts/run_tests.py` remains available only for the explicitly selected Python environment, not as the legacy-runtime default. Pass pytest paths after `--` only when preserving equivalent isolation and runtime. The runner blocks database drivers and network sockets in the current Python process before test discovery. Before invoking it, inspect test imports and identify every repository, shared-fixture, addon, and sibling-test import root. The `--addon` mode scopes pytest discovery but does not add those project paths to `PYTHONPATH`; export only the required paths, keeping container paths consistent with the mounted repo. If collection fails on a helper or compatibility selector import, treat it as an invocation/setup error, correct `PYTHONPATH`, and rerun before classifying the product tests. If pytest's package discovery imports the addon root `__init__.py` and that bootstraps Odoo before collecting offline tests, classify it as a collection-boundary/setup error; do not edit package initialization solely to make pytest collection work. Use the prescribed runner, or run supported standalone `unittest` discovery from the test directory with the same isolation hook and report it as supplemental evidence—not as a substitute for the required runner or native Odoo integration tests. Run strict AC selector scripts through their documented entrypoint and distinguish `COMPONENT PASS` from AC/UAT acceptance; excluded or unavailable cases remain `NOT RUN`. For project code, copy the helper and runner or put this skill folder on PYTHONPATH and run the target tests under the runner. Report both results and mock limitations. Before mocking a controller route, inspect the target Odoo 13 dispatcher/route signature and test the exact argument mapping it applies, including query and form values forwarded as `kwargs`; a hand-built fake request that omits dispatcher arguments can make a valid POST look impossible or let a broken route pass. For layered guards, test each layer separately: an HTTP request rejected by an earlier transport/security guard cannot prove a later query/body/dispatch branch; keep the integration assertion scoped to the rejection it actually reaches, and exercise downstream branches with a focused controller-unit test using an explicit secure request and dispatcher-mapped arguments. Assert the guard ordering and whether the protected helper was invoked. For credential-bearing routes, test the allowed header/body channel and explicit rejection of query or disallowed body channels. Use a real Odoo integration environment separately for ORM, permissions, transactions, SQL, scheduling, routing, and database behavior.

See [addon layout and runner](references/addon-layout.md) for setup and collection constraints.
