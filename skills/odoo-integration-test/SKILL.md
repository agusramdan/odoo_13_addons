# Odoo 13 integration testing

## Task-specific resource naming

Name every integration-test database, task-built image/tag, and container with the exact task number or a consistently sanitized form of its identifier (for example, task `ADDONS13-79`: database `uat_addons13_79`, image tag `local/odoo-uat:addons13-79`, container `db-addons13-79`) to distinguish concurrent tasks and avoid collisions. Add a run-specific suffix when needed; validate database identifier limits and check existing resources before creation. A name is not proof of ownership or disposability: record exact created IDs and clean up only resources verified to belong to the run. Respect explicit Owner-selected names and existing authorization; do not rename or remove another task's resources.

## `/runuat-odoo13` command

When invoked through `/runuat-odoo13 <task identifier>`, treat the command as the Owner's instruction to configure and execute UAT automatically for the uniquely identified task, within its accepted scope and safe, synthetic-only, isolated disposable resources. Derive safely available settings without asking for redundant configuration approvals; use the documented resolver and repository wrapper as applicable. Follow the most recent direct Owner instruction, any stricter task rule, the exact approved candidate and accepted tests; a newer no-runtime/no-database/no-build instruction remains binding until explicitly superseded. Never access production, reset an attempt ledger without separate explicit permission, or guess isolation, ownership, approval, missing dependency artifacts, or test outcomes. When blocked, identify the concrete missing precondition, attempt authorized read-only discovery and preparation, and report affected actuals NOT RUN; do not substitute an offline check for real UAT. The slash bundle loads this skill but does not itself implement or guarantee an automated execution controller; test actual interactive dispatch separately from mocked-dispatch and runtime evidence.

A direct `runuat` or `/runuat` for one uniquely identified task authorizes automatic safe, isolated, synthetic disposable setup and execution only within the accepted task scope; do not ask for redundant configuration confirmations. Later explicit stops and stricter task-specific instructions override it. This does not authorize arbitrary network access, production data, expanded scope, or risky cleanup. Missing acceptance or semantic safety evidence remains a blocker.

`scripts/auto_uat.py [task]` is a fail-closed CLI: it always reports BLOCKED and never runs UAT. Its fake-only in-memory model exercises gate ordering, not real authorization, atomic locking, evidence verification, isolation or execution. No trusted dispatcher or live adapter exists; forged CLI arguments and test fixtures cannot establish authorization. Integrating an authenticated chronology-aware dispatcher and independently verifying all live gates remain necessary before real automation can be claimed. Never interpret SIMULATED_PASS as a UAT result.

The read-only `scripts/resolve_uat.py --repo <root> --task-id <id> --profile <repo-relative-json> --profile-sha256 <sha256>` produces a bounded configuration proposal from a committed JSON profile and the planner's inventory. Profile fields: `task_id`, `database`, `runtime` (e.g. `python3.8`), `max_runs`, `profile` (`uat-native` or `uat-offline`), `data` (`synthetic`), `egress` (`denied`), `host_ports` (`disabled`), `database_lifecycle` (`disposable`), and `cleanup` (`exact-run-owned-only`). The hash establishes byte identity only, not acceptance; every profile is unverified. It does not verify Compose isolation, artifacts beyond that profile, occupancy, wrapper, ledger or authorization and cannot execute or approve UAT. It does not create or reset ledgers. Never pass secrets.

For a read-only preliminary candidate inventory, run `python "$HERMES_HOME/skills/odoo13-integration-test/scripts/plan_uat.py" --repo <repository-root> --task-id <task-id>`. See `--help` for optional, non-secret bindings. The planner runs Git inspection only, hashes staged and worktree changes, blocks sensitive changed paths, and never approves or executes UAT. Treat its repeated inventory as a race check, not an atomic snapshot; revalidate immediately before any separately authorized action. Inspect hidden Git index flags and reject incomplete inventories, use literal pathspecs for staged filenames, and do not follow symlinked parent directories when hashing worktree files because each can conceal or redirect candidate bytes. Ignored files and resource occupancy are not verified. Do not supply secret values as arguments. The planner does not reset or initialize attempt ledgers.

Place integration tests for each addon in `<addon>/tests/integration/` and retain existing unit and integration tests. Follow [layout and discovery](references/layout.md): Odoo 13 requires the top-level `tests/__init__.py` to import each `test_*` module directly; importing only the nested `integration` package may silently yield zero collected tests. Use actual Odoo `TransactionCase`, `SavepointCase`, or `HttpCase` as appropriate. Exercise real ORM, access control, workflow, cron method, wizard, or HTTP interactions; mock external APIs and irreversible side effects. Prefer meaningful assertions and failure paths. For HTTP tests, verify the test client's resolved scheme/headers and handler guard order. If a TLS check runs before query/body/auth validation, a cleartext rejection cannot prove those later paths, and a success test cannot pass through that transport. Use a verified HTTPS fixture or test handler logic separately; do not claim the latter proves transport/TLS behavior. In Odoo 13, `HttpCase.url_open()` constructs an `http://` URL; `X-Forwarded-Proto: https` alone does not make `request.httprequest.is_secure` true. The WSGI `ProxyFix` path also requires `proxy_mode=True` and `X-Forwarded-Host`. For a trusted-proxy simulation, configure this only in the isolated test server, verify the resolved scheme, and report it as handler-under-proxy-metadata coverage—not proof of TLS transport. See [scenarios](references/scenarios.md).

For intentional `sudo()` in tests, add an adjacent concise comment naming the ACL/record-rule boundary and the fixture operation that needs elevation. First inspect how the recordset is used: if it only supplies `type(recordset)` for a class-level patch, use the ordinary environment recordset instead; `sudo()` does not change the model class and adds no access coverage there. Remove unnecessary elevation rather than documenting it as required. A comment explains the test boundary but does not replace review of the privileged operation.

Before preparing a suite, treat accepted PRD/UAT files as separate hash-bound specification inputs: read them at their recorded paths and verify exact hashes, then inspect source/test code using `git show <candidate>:<path>`; do not require the specification files to exist in the code commit or treat later document addition/acceptance as a candidate rebind. Atomize semantically—not by punctuation—into every distinct actor, value/type, order, positive/negative control, state transition, boundary, or administrative deliverable required by the accepted oracle; expand cross-products only where the UAT requires them. Map each atom to its exact test path/class/method, active assertion, fixture and discovery boundary, or explicitly mark `NO ADEQUATE ASSERTION FOUND` / `NOT ASSESSED` with inspected scope. An enumerated case or partial assertion is not complete coverage or PASS. For large matrices, partition case families into non-overlapping files, give each worker the exact accepted artifact hash and no-runtime boundary, then reconcile their case-ID sets and atomic coverage against the current accepted document programmatically; keep missing or unexamined suboracles explicitly NOT ASSESSED, and independently review the combined result because a count of mapped cases can hide missing assertions. When consolidating amended UAT into a history-free document, retain applicable predecessor oracles and explicit supersessions, verify each fixture, actor, negative control and decision gate independently, and label the new document unaccepted until its exact hash is approved; preserve original actuals in their original evidence rather than converting them to new-run results. Keep unexamined items explicitly NOT ASSESSED and distinguish static source evidence from native execution. If registration conflicts with an existing unit guard, inspect both contracts and the target loader before proposing a minimal change; do not bypass the guard with a syntactic alias or weaken its assertions merely to make discovery appear complete. Under an explicit no-runtime gate, continue independent static mapping and preparation but mark loader behavior and UAT NOT RUN until authorized. Before narrowing a suite, compare test files and methods against the candidate base/HEAD. Never delete or skip an existing test to isolate out-of-scope failures; preserve it and report the raw result under its owning scope. If the candidate intentionally privatizes or renames an API, adapt only the test call path as needed while preserving its assertions. When a prerequisite assertion fails before a later behavior is reached, mark that later behavior NOT EXERCISED. After changing test inventory, if database reuse could skip tests, bind the final run to a fresh disposable database under the separate runtime/database authorization described below.

When the Owner asks to simplify or focus on existing Python integration tests, inventory the existing candidate-bound test modules, static import chain and known runner first; propose a bounded preliminary run without waiting for the full UAT crosswalk, unless an applicable gate actually requires it. Present environment approval separately from UAT scope, coverage, candidate rebind and risk decisions: describe the image/dependencies, disposable database, network isolation, resource limits and cleanup in concise plain language. Honor any explicit no-runtime or configuration-approval restriction before running. Report actual collected identities and outcomes only for the executed subset; uncollected tests, full UAT and unrelated open decisions remain unverified, not waived. Avoid repeated large mapping rounds when the requested next step is a narrower initial test run.

For RPC method-boundary/security tests, invoke the Odoo 13 service entry point (`odoo.service.model.execute` / `execute_kw`) and assert the dispatch outcome; calling `check_method_name` directly tests only the guard, while calling `execute_cr` directly bypasses the outer method-name check. Label this accurately: service-entry testing does not prove HTTP/session authentication; use `HttpCase` when that wire/authentication boundary is part of the claim.

For a uniquely identified task, treat the user's direct request to run UAT as authorization to derive configuration and execute within the task's accepted scope using an isolated, synthetic, disposable environment; do not request redundant approval for safely derivable configuration. If the Owner requires approval of the final configuration before builds, containers, database access or tests, preparation and a candidate/specification rebind do not constitute that approval; complete only authorized static preparation and present the actual final configuration before runtime. Reuse prior explicit selections, but stop if target identity, ownership, isolation, accepted cases, or attempt budget cannot be established; never infer approval to reset a ledger, access production, or broaden cleanup. When a later candidate changes only test infrastructure, compare the exact commit delta and recheck the accepted PRD/UAT hashes; obtain explicit rebind to the new candidate if the acceptance is candidate-bound, preserving the oracle and historical actuals. Reuse a prior ledger only if its active generation and scope are verified or the Owner explicitly approves that binding; preserve its count and never infer a reset from rebind. Record these separate decisions with candidate, artifact hashes, ledger generation and no-reset boundary, then read them back before execution. Honor any later explicit stop or narrower task-specific restriction. The preliminary planner is read-only and does not itself configure or execute UAT; do not claim that automatic execution exists until its implementation and preflight are verified.

Integration tests require a real Odoo 13 installation, registry and PostgreSQL. Use a dedicated disposable database and isolated services; module install/update modifies the database outside individual test rollbacks. Never target production or infer that a database is disposable from its name. Immediately before any state-changing UAT action, resolve the exact chronology of user messages—including explicit task-list status—against the current authorization; do not rely on an assistant summary to decide whether authorization is active. A clear later cancellation, `NOT RUN`, or no-database direction supersedes earlier authorization and requires stopping before resource creation or runner invocation. A clear later reauthorization may supersede that cancellation only within the explicit scope and limits already authorized. Do not treat vague phrases such as “remove obstacles” as sufficient to reverse a concrete stop instruction; if the latest intent is genuinely ambiguous, ask one targeted question before any side effect. A request to ignore prohibitions never overrides system/developer safety requirements. Complete read-only candidate, image and isolation preflight before any state-changing action; a later cancellation or no-database instruction supersedes earlier authorization. Failed prerequisites mean stop, not repair-and-retry. For the bundled runner, use `scripts/run_integration.py` with `--ack-test-db` and [running](references/running.md); for repository Compose UAT, follow [Guarded Compose UAT](references/guarded-compose-uat.md). For each native Compose UAT, build a fresh task/candidate-specific final Odoo image from the approved local source, pinned base and complete lock; never use another task's prebuilt final image. Use the Owner-selected PostgreSQL 10 service image, pulling only `postgres:10` when absent and then pinning its resolved digest. Follow [Guarded Compose UAT](references/guarded-compose-uat.md) for the offline Odoo build gate and image provenance. Verify logs show the intended tests actually ran, then report candidate, per-case results, database/cleanup and gate status separately. A partial subset is not PASS.
