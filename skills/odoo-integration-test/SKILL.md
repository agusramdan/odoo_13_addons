# Odoo 13 integration testing

Use this skill as the default workflow for Odoo 13 integration testing and integration-test UAT, unless the Owner explicitly selects another workflow. Honor task-specific scope, approvals, and safety restrictions.

## Task-specific resource naming

Name every integration-test database, task-built image/tag, container, network, and evidence/ledger directory with the task identifier or a consistently sanitized form; when reusing a procedure, replace task-specific names rather than copying them. Add a run-specific suffix when needed; validate database identifier limits and check existing resources before creation. A name is not proof of ownership or disposability: record exact created IDs and clean up only resources verified to belong to the run. Respect explicit Owner-selected names and existing authorization; do not rename or remove another task's resources.

## Reuse a working direct-Docker method

Inspect the actual sanitized runner evidence and resource lifecycle before dismissing a previously working method. A proven native path uses an internal-only Docker network, disposable PostgreSQL with tmpfs data, a read-only task snapshot, the integration runner, and explicit database/container/network cleanup and readback. Adapt resource names and secrets for the current task; protect secret files and bind the current candidate and attempt budget. Prior execution proves the method is viable, not that another candidate or the full UAT passed. Check the actual PostgreSQL entrypoint and capability policy: dropping all capabilities can prevent a root entrypoint from switching to the database user. Verify interpreter versions against the exact pinned image ID in an authorized isolated probe, not against a tag or an unrelated image.

For reusable integration-test automation, prefer convention over configuration: accept the task ID and addon as the normal inputs, derive safe task-scoped names and unambiguous existing paths from established conventions, and expose overrides only when necessary. Never infer acceptance, source identity, an attempt reset, or resource ownership from a name; stop with the concrete ambiguity when those cannot be established. Verify the real execution, exit status, failure reporting and cleanup with an isolated synthetic addon before advertising a new runner as ready; mock-only tests and a preflight prototype do not demonstrate a working Docker lifecycle.

## Direct Docker integration runner

For an authorized task and addon, use `python3 "$HERMES_HOME/skills/odoo-integration-test/scripts/run_odoo13_docker.py" --task-id ADDONS13-72 --addon amr_sentry` (substitute the actual task and addon). This runs native integration tests; its success is not full UAT acceptance. It requires an existing mode-0600 task record at `$HERMES_HOME/uat-state/<TASK>/integration-runner.json`: when absent, derive and create it only from verified task decisions and current source identity, rather than asking the Owner for values already available. Record `task_id`, `snapshot`, `manifest_sha256` (the script's `tree_hash` value, not a Git or manifest-file hash), `ledger`, `max_attempts`, `database`, `odoo_image_id`, `postgres_image_id`, and `addons: {"<addon>": {"test_tags": "/<addon>"}}`. The snapshot can contain addons at its root or in `addons/`; exactly one layout must contain the target. Bind the record to the accepted current candidate, image and existing authorized ledger; do not invent approval or create/reset a ledger. Before execution check the task metadata and exact approved cap against the record: the script checks its record but does not independently prove user authorization, spec acceptance, image provenance, or the cap. Recreate or update the task record after an authorized candidate change, without changing the ledger. Use synthetic-only data, no host ports, local pinned images and an internal Docker network; the runner reserves one attempt before creating resources, does not retry, writes a private log and verifies removal of labeled run-owned containers/networks. Inspect evidence and cleanup, and preserve failed actuals. The runner needs noninteractive `sudo chown` for a private generated Odoo config. A synthetic Odoo/PostgreSQL 10 smoke and 11 offline tests passed; an earlier synthetic startup failed before database creation, so a later clean smoke does not erase that failure. Do not use this script as proof of complete UAT or as a replacement for accepted case mapping. Runtime and cleanup remain subject to fresh task-specific preflight and any newer Owner restriction.

## `/runuat-odoo13` command

When invoked through `/runuat-odoo13 <task identifier>`, treat the command as the Owner's instruction to configure and execute UAT automatically for the uniquely identified task, within its accepted scope and safe, synthetic-only, isolated disposable resources. Derive safely available settings without asking for redundant configuration approvals; use the documented resolver and repository wrapper as applicable. Follow the most recent direct Owner instruction, any stricter task rule, the exact approved candidate and accepted tests; a newer no-runtime/no-database/no-build instruction remains binding until explicitly superseded. Never access production, reset an attempt ledger without separate explicit permission, or guess isolation, ownership, approval, missing dependency artifacts, or test outcomes. When blocked, identify the concrete missing precondition, attempt authorized read-only discovery and preparation, and report affected actuals NOT RUN; do not substitute an offline check for real UAT. The slash bundle loads this skill but does not itself implement or guarantee an automated execution controller; test actual interactive dispatch separately from mocked-dispatch and runtime evidence.

A direct `jalankan UAT` or `/runuat` for one uniquely identified task authorizes automatic safe, isolated, synthetic disposable setup and execution only within the accepted task scope; do not ask for redundant configuration confirmations. Later explicit stops and stricter task-specific instructions override it. This does not authorize arbitrary network access, production data, expanded scope, or risky cleanup. Missing acceptance or semantic safety evidence remains a blocker.

`scripts/auto_uat.py [task]` is a fail-closed CLI: it always reports BLOCKED and never runs UAT. Its fake-only in-memory model exercises gate ordering, not real authorization, atomic locking, evidence verification, isolation or execution. No trusted dispatcher or live adapter exists; forged CLI arguments and test fixtures cannot establish authorization. Integrating an authenticated chronology-aware dispatcher and independently verifying all live gates remain necessary before real automation can be claimed. Never interpret SIMULATED_PASS as a UAT result.

The read-only `scripts/resolve_uat.py --repo <root> --task-id <id> --profile <repo-relative-json> --profile-sha256 <sha256>` produces a bounded configuration proposal from a committed JSON profile and the planner's inventory. Profile fields: `task_id`, `database`, `runtime` (e.g. `python3.8`), `max_runs`, `profile` (`uat-native` or `uat-offline`), `data` (`synthetic`), `egress` (`denied`), `host_ports` (`disabled`), `database_lifecycle` (`disposable`), and `cleanup` (`exact-run-owned-only`). The hash establishes byte identity only, not acceptance; every profile is unverified. It does not verify Compose isolation, artifacts beyond that profile, occupancy, wrapper, ledger or authorization and cannot execute or approve UAT. It does not create or reset ledgers. Never pass secrets.

For a read-only preliminary candidate inventory, run `python "$HERMES_HOME/skills/odoo-integration-test/scripts/plan_uat.py" --repo <repository-root> --task-id <task-id>`. See `--help` for optional, non-secret bindings. The planner runs Git inspection only, hashes staged and worktree changes, blocks sensitive changed paths, and never approves or executes UAT. Treat its repeated inventory as a race check, not an atomic snapshot; revalidate immediately before any separately authorized action. Inspect hidden Git index flags and reject incomplete inventories, use literal pathspecs for staged filenames, and do not follow symlinked parent directories when hashing worktree files because each can conceal or redirect candidate bytes. Ignored files and resource occupancy are not verified. Do not supply secret values as arguments. The planner does not reset or initialize attempt ledgers.

Before using an integration runner's `--dry-run` on Python 3.7, inspect its formatting path: `shlex.join` is unavailable on that interpreter and may fail after command validation even though it is not the test-execution path. For a safe command-only diagnostic, import the runner without invoking `main`, call `build_command()` with nonsecret arguments, and inspect the returned argument list; this validates construction only, not Odoo, database access or UAT. If a runner change is authorized, use a Python-3.7-compatible POSIX rendering such as `' '.join(shlex.quote(arg) for arg in command)` and test the actual target interpreter.

Place integration tests for each addon in `<addon>/tests/integration/` and retain existing unit and integration tests. Follow [layout and discovery](references/layout.md): Odoo 13 requires the top-level `tests/__init__.py` to import each `test_*` module directly; importing only the nested `integration` package may silently yield zero collected tests. Use actual Odoo `TransactionCase`, `SavepointCase`, or `HttpCase` as appropriate. Exercise real ORM, access control, workflow, cron method, wizard, or HTTP interactions; mock external APIs and irreversible side effects. Prefer meaningful assertions and failure paths. For HTTP tests, verify the test client's resolved scheme/headers and handler guard order. If a TLS check runs before query/body/auth validation, a cleartext rejection cannot prove those later paths, and a success test cannot pass through that transport. Use a verified HTTPS fixture or test handler logic separately; do not claim the latter proves transport/TLS behavior. In Odoo 13, `HttpCase.url_open()` constructs an `http://` URL; `X-Forwarded-Proto: https` alone does not make `request.httprequest.is_secure` true. The WSGI `ProxyFix` path also requires `proxy_mode=True` and `X-Forwarded-Host`. For a trusted-proxy simulation, configure this only in the isolated test server, verify the resolved scheme, and report it as handler-under-proxy-metadata coverage—not proof of TLS transport. See [scenarios](references/scenarios.md).

When a UAT case requires Odoo test-mode ON/OFF, discovery, and negative selectors, test the Odoo loader and execution controls themselves; Sentry reporter policy ON/OFF or mocked telemetry does not prove test registration or discovery. Bind any response-identity assertion to the specified seam: spy on the actual dispatcher-to-hook call while preserving the real hook, and assert the same object there; do not require a downstream reporter to receive an argument that its contract intentionally drops. A written test or static registration is not a native execution result.

When the agreed integration oracle requires a real client-to-dispatcher path, construct the client, endpoint and credential as synthetic ORM records and invoke the actual factory and request-preparation path; mock only the transport and telemetry seams permitted by the specification. In the inspected `amr_service_client` implementation, `ServiceClient` exposes `endpoint`, not `endpoint_id`; `prepare_payload()` passes `self.endpoint` as `endpoint_id` to `ServiceClientSend`. Tests constructing the sender directly without that argument can fail in the constructor before exercising the hook; inspect the exact candidate implementation and prefer its actual call path rather than adding an attribute to the dependency to satisfy the fixture. Before declaring a proposed integration fixture adequate, trace from ORM record through factory and request preparation to the dispatcher: a wrapper that supplies its own prepared context can exercise a real hook yet bypass the actual client/dependency boundary. Do not replace request preparation or the client under test with a hand-written adapter and call it end-to-end integration: the adapter bypasses the very boundary being verified. Keep isolated fake-based unit tests separate, trace registration to the native Odoo loader, and report authored or statically reviewed integration tests as NOT RUN until exercised on an authorized Odoo/DB runtime. Observe response identity at the exact seam named by the oracle; do not infer that downstream telemetry receives fields its contract intentionally drops.

For transaction and cleanup oracles, separate same-cursor state from committed or independent-cursor visibility: use an explicitly approved isolated fixture and savepoint or fresh-cursor strategy, and never commit or roll back the framework-owned test cursor to manufacture persistence. To exercise rollback through a savepoint, raise a dedicated sentinel inside the savepoint and catch it outside; normal context exit releases the savepoint and does not roll back. Before adding any ORM flush call, inspect the exact target Odoo version's `BaseModel` source and signature rather than assuming a newer API exists; syntax compilation alone cannot detect a missing runtime method. A writer-failure test must distinguish reporter-call count from error-writer-call count; `assert_called_once_with` already asserts the reporter's total call count, but does not count a different writer. Treat authored rollback/cleanup tests and same-cursor searches as static design until the authorized database run proves visibility and exact run-owned resource cleanup. Before building another cleanup prototype, inspect the existing approved wrapper's actual project-occupancy, attempt-ledger, ownership and cleanup controls against the accepted oracle; a mock-only controller or cleanup-only adapter is not evidence of an integrated live creator/cleanup path. A unique, verified-empty Compose project plus project-scoped cleanup and post-cleanup readback may satisfy run-owned cleanup; do not invent an exact-resource-ID requirement if the accepted oracle and current standard do not require it. If the user requires stopping on an uncovered oracle, report that exact gap and preserve the attempt budget rather than repeatedly creating disconnected mock harnesses or claiming live readiness.

When the Owner directs removal of a test-entrypoint directory that an accepted UAT still names, inventory its scripts, registrations, callers and assertions across the repository before editing; distinguish unique coverage from adapters to canonical tests. Preserve the accepted specifications, prepare a versioned amendment mapping affected cases and replacement selectors, and obtain acceptance of its exact hashes before executing a scope-changing deletion. Do not delete adjacent addon tests or silently replace a missing oracle with a passing count. When the Owner removes a specific UAT failure-injection case, distinguish removal of that case from operational cleanup safeguards: retain project ownership, empty-project preflight, scoped cleanup and post-cleanup readback unless separately changed under the governing safety rules. Preserve historical NOT RUN/FAIL evidence; removal is neither a passing result nor blanket risk acceptance. Revise unaccepted amendments when the Owner corrects the attempt budget, preserving earlier versions and applying the latest explicit decision.
